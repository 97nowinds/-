## 真正同帧的 960 与 2K 对照

在集群 GPU 0 重新运行实际 YOLO/ByteTrack（每五个录像帧处理一次，cam_2 使用现有 guarded tracker），
得到固定新人体框与局部轨迹。随后对同一帧/同一目标分别使用 960 缩图和 2560 原图做人脸识别。
两种人脸流程各自维护融合/投票，三路互相不传身份，不使用入口继承，未执行全局身份锁。
0.8 秒固定目标轮询用于对照，不完全复刻在线时序；因此离线局部编号与在线编号不同。

## 轨迹与地图的边界

在线轨迹抽样记录出现多次局部/全局编号变化。例如 cam_2 的局部 79 对应 person_9，
之后局部 91 对应 person_27，再后局部 99 对应 person_44。
在用户说明的单人场景下，这已表明系统没有维持全程同一个轨迹编号；其中也可能含误检/重复候选。
摄像头离开视野造成的空框间隔，与在视野内漏检需要结合连续视频进一步区分，不能统称为丢人。

本次观察器没有保存 API 中独立的 identities 和 floor_map.people 字段；
yolo_tracks 本身不含姓名/位置字段。因此日志里 person_id/name 为空不表示实际界面一定没有姓名。
本轮不能精确计算在线姓名保持时长、每秒地图位置或跳点距离；也不能给出全程姓名零丢失的结论。
后续验收需补齐这些发布字段，绑定源帧信息，并分别统计人脸确认、身份锁、轨迹合并和地图发布。

## 剩余原因与下一步

1. cam_1 缺少可用人脸观察：高清无法消除背脸/俯视问题，应先核对有效朝向机会与检测 ROI。
2. cam_2 能看见脸但大多比对不过：检查有效脸的角度、清晰度以及注册样本覆盖；不直接放宽身份阈值。
3. 快速经过/局部 ID 变化使可靠投票分散；需要区分可恢复的轨迹与身份锁冲突，不能直接把姓名交给最近框。
4. 人脸恢复必须与轨迹关联、全局单人归属和地图发布分别验收。认出注册人员不等于前后全局轨迹自动合并。

本轮只停止录像、读取诊断并执行隔离回放；未再改变线上算法、阈值或摄像头配置。
