## 已查明的问题

1. 本机 15002 实际是三路实时识别程序，使用 CPU，诊断时约占 8 个逻辑核；8765 也占用本机 CPU/GPU。整机 CPU 采样达到 100%。
2. 地图 `/health` 原先依赖上游 API；上游可正常返回但超过常驻检查的 2 秒时限，会被反复重启。已把本地存活检查与上游业务可用性分开。地图和位置接口仍如实返回上游故障。
3. 常驻检查超时从 2/3 秒调整为 8 秒，保留连续失败与重启策略；启动异常写入 `runtime/resident-startup-error.log`，避免 pythonw 静默失败。
4. 原录像链路也出现过 HEVC 参考帧错误与 RTSP 读取超时。迁移不能证明已经根除摄像头、网络端所有卡顿。

## 迁移边界与数据

- 复制实际运行的两个 Windows 副本，未用本仓库代码覆盖它们。
- 对可复用大文件核对 SHA-256 后复用，共匹配 12 个权重文件；MiniCPM 权重约 2.6 GB。
- 8765 原有 Pascal 专用运行限制在集群副本中放开到兼容 CUDA 架构；保持 float16、math SDPA、原权重与提示词。
- 15002 原接口返回的人员库为空；原主项目 15001 保留 8 名已注册人员。两份库未自动混合。
- 停止本机发送器和旧接收器后，用 SQLite backup 取得一致性备份。迁入记录：handoffs 2138，delivery_attempts 2139，interaction_decisions 87，durable_jpeg_inputs 2138。`integrity_check` 通过。后续实时输入会继续增长。
- 历史证据图片及原输入缓存留在原 Windows 部署目录，未宣称已把全部历史图片搬到集群。原数据和源码备份保留；数据库记录迁移不等于每张历史图片都可从新主机下载。
- RTSP URL 在集群改用现有的本机回环发布流；摄像头密码不出现在启动参数、文档或 Git。
- 8765 保留 `source_frame` 模式，使用原冻结 JPEG 与原快照、人物、时间绑定。HTTP 连接仅针对原允许的 `127.0.0.1:5177` 改为集群回环 25177，URL 白名单、Bearer、JPEG 哈希、尺寸、TTL 仍校验。
- 不把未确认的图像对齐或时钟校验改成已确认，不伪造交互结论。

## 常驻方式

Windows 计划任务：

- `Lab Safety Frontend Watcher`：原展示服务、主项目隧道、三路摄像头发布。
- `Lab Interaction Cluster Bridge`：15002/8765 本地转发与 25177 反向图片转发。仅重启自己创建的 SSH 进程。
- `Lab Joint Frame Recorder`：原冻结帧发送器；已选择集群接收模式，禁止在隧道故障时自动重新启动本机 CPU/GPU 接收器。

lnx 用户 systemd：

- `lab-joint-15002.service`
- `lab-joint-8765.service`

两服务启用失败重启与用户启动自动拉起。Windows 任务依赖当前用户登录；不能把“关机、断网或用户退出后仍可监控”作为保证。

凭据仍在本机受保护存储以及集群权限 0600 的私有配置中，不写入本文或版本库。

## 维护与回退

1. 修改或停用服务前先检查对应计划任务与进程身份，不能按端口盲目结束其他进程。
2. 需要回退 8765 时，先暂停 `Lab Joint Frame Recorder`，将集群最新数据库以 SQLite backup 导出并取回；不能直接用迁移前备份覆盖新产生的事件。
3. 停止 `Lab Interaction Cluster Bridge` 以释放本机端口，保留原 Windows 源目录、模型与受保护凭据。
4. 原发送器源码备份在原部署目录 `runtime/resident_joint.before_cluster_migration.py`；恢复原脚本与接收器运行模式后，按原环境启动两套服务。核验后再恢复发送器。
5. 集群停止新建的两个 systemd 单元即可；不触碰原主项目 `lab-safety-api`、5000 或其他 GPU 任务。
