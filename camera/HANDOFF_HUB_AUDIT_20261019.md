日期：2026-10-19。本文区分已复现的代码缺陷、录像证据、已部署修复和仍在评估的策略。

## 1. 审查方法与完成范围

按操作者描述，这个实验室只有一处实体出入口，主通道、侧通道、副通道之间的人员通行交接集中在该区域。策略应表达这个共同区域，而不是把每一种通行方向都写成独立且僵硬的路线。但同一名实验人员被两路相机同时看见也可能是静止的共同观测，不能一律解释为过门；更不能因为两个人都靠近门就把他们合并。

人工审查以衣着、动作、遮挡前后连续性和相机时间对应为依据，以匿名人员区分。项目输出的姓名、local ID、global ID 均不是人工真值；不根据人脸猜真实姓名。不再以参与人员名单作为开始审查的前提。

模型推理、录像解码、统计、对照测试、证据图生成均在 lnx 集群执行；本机仅编写/传送源码、读取结果和查看集群生成的证据图。ReID 仍使用原 OSNet-x1.0 MSMT17 权重，没有换模型或降低全局 ReID 身份门限。

## 2. 已查实的问题

### 2.1 多相机共用 ByteTrack ID 计数器，初始化/重连会相互影响

检查集群实际安装的 Ultralytics 8.4.121：`BYTETracker.__init__` / `reset` 调用 `reset_id`，`STrack.reset_id` 会重置公共 `BaseTrack._count`。另一台相机随后产生的新目标可能复用本相机仍在使用的局部编号。

已用确定性测试复现计数器重置和 ID 复用机制。旧服务累计重连计数曾为 Cam1 16、Cam2 10、入口 0；这使该问题值得优先修复，但不等于每次现场串号都已被证明由它引起。

修复：`scoped_byte_tracker.py` 为每个相机跟踪实例提供独立、带锁的单调编号器，重连只清轨迹，不回退编号。普通和 guarded ByteTrack 共用这一编号隔离层，保留安装版本的匹配/更新算法。编号的实际键仍是 `(camera_id, local_id)`，不是把 local ID 当跨摄身份。

涉及：`ScopedByteTracker`、`TrackIdAllocator`；`guarded_byte_tracker.py:GuardedByteTracker`；`yolo_person_tracker.py:YoloPersonTracker.__init__/track/reset`。

### 2.2 遮挡后产生的临时片段，第一次恢复失败后不再充分重试

原有协调器可能先给遮挡片段一个临时 global ID，随后因已绑定而退出本相机恢复候选流程。人在分开后，即使外观重新清楚，也可能保留错误的分裂状态。另有重叠的旧完整框/新半身框被提前记作“两个不同的人”的情况。

修复：增加局部恢复待确认状态，使临时片段在有限时间内继续收集证据；同帧重叠且样本不干净时不立即形成永久的不同人约束。运动、外观、竞争候选差距、同相机单一占用约束继续生效。证据不足保持临时/未知，不通过脚点距离直接转交姓名。

涉及：`CrossCameraTrackCoordinator._same_camera_relink_assignments/update_batch/forget_local/forget_camera/reset_replay_cycle`。

### 2.3 外观图库质量门限与旧单向量回退不一致

原路径中，不合格样本可能被图库拒绝，却仍写入旧单向量缓存；重复或被拒的样本也可能使缓存观测时间变新。图库保护因而没有覆盖全部身份匹配入口。

修复：质量门限提前到提取/入库入口；单向量回退来自真正获准的图库代表特征，观测时间保留图库实际更新时刻。单独记录提取尝试时间，避免重复样本不入库导致每帧反复推理。半身和遮挡混合裁剪不覆盖干净的全身身份图库。

涉及：`CrossCameraTrackCoordinator.update_batch`、`local_features/local_feature_attempts/local_galleries`。

### 2.4 已消失的全局轨迹仍占用注册姓名锁

旧全局人体轨迹已经删除，但姓名锁仍可能在其保留期内拒绝新轨迹上已经由人脸模块确认的相同注册身份。

修复：只在旧 global track 确实不存在、新 global track 存在、且传入身份已是 `identity_source == face` 的确认身份时允许转移锁。旧人体仍存在时继续拒绝；仅凭 handoff 或空间接近不能抢占身份。这不会把旧轨迹历史和新轨迹无条件合成。

涉及：`CrossCameraTrackCoordinator.set_identity`。

### 2.5 既有交接门限确实拒绝了单人正常通行

单人 88.9 秒录像中，原路线出现 1331 次目标未进入 gate、906 次源未进入 gate 的候选拒绝。统一区域候选版降为 10 和 3 次。这里的数字是候选评估次数，不是丢人次数，也不代表准确率提升比例。

统一区域版本利用原有人工标注的图像多边形合并入口区域，并允许实际人体框与区域的重叠作为脚点缺失时的辅助证据。没有重画平面图、仪器区域或地图距离标定，没有全局放松 ReID 门限。高分候选仍要求多次真实观测确认。

但五组短录像的结果并非全部改善：部分静止工作/多人遮挡片段仍有更多 global ID 分裂。因此这项策略仍是候选，**实时配置 `enabled=false`**。

涉及：`handoff_hub.py:load_handoff_transitions/body_overlap_ratio`；`association.py` 的图像 gate 评估；`config/handoff_policy.json`。

### 2.6 有些剩余丢失发生在外观分数层，而非路线或速度

单人录像约第 87.12 秒：统一区域版本两侧 gate 均已通过，实际图库 ReID 得分约 0.484，best 约 0.513，低于 medium 0.52；之后约 87.96 秒提高到约 0.557，但未满足当时重叠关联要求的高门限。目标在入口画面的左/下边缘被截断，视角和可见身体部分变化明显。

该段相邻候选源/目标观测时间差约 0.004～0.03 秒。这段证据不支持“仅因人物走太快或传输延迟而断号”的解释，也不能因此对所有拥挤场景放松外观门限。原 ReID 模型没有替换；这部分仍未完全解决。

逐帧推理对照也未在所有短录像中减少碎片，故本轮不直接全局改成每帧推理或降低匹配阈值。

### 2.8 人脸阶段：主要损失发生在没有合格人脸，而非一次 ArcFace 计算耗时

三路 CameraWorker 的单人原速回放完整结束，入口 63 次人脸尝试：25 次 `no_face`、26 次 `face_too_small`、3 次 `score_or_margin_rejected`、9 次 `known_candidate`。后者是候选观测次数，不是 9 个不同人员或最终准确率。

检测和识别 ONNX Session 实际使用 CUDAExecutionProvider。现有最小人脸质量和多次确认要求意味着短暂、侧脸、小脸不一定能完成注册身份确认。没有为了表面上“更容易认出”而降低实名匹配的安全阈值。

### 2.9 启动时整读事件日志导致内存膨胀

原日志加载使用整文件读取，历史文件曾达 7.16 GB，导致启动内存大幅增加。部署前活动日志又已约 1.39 GB。

修复：小文件流式加载；大文件从末尾按块获取有限条近期事件，完整原文件归档后保留有限活动尾部，维持事件 sequence。部署后原 1,390,417,556 字节活动日志已完整归档，活动日志约 182 KB（检查时刻），未删除历史。更早的约 7.16 GB 原归档也仍保留。这是启动内存修复，不是无限期的磁盘保留管理。
